# U-154 — Move and hold orders keep a facing

Epic: Squad command (Conflict parity). Pillar: P2.
Size: S. Human verdict: none (engineering criteria only).
Status, priority, dependencies and branch/PR live in [BACKLOG.md](../../BACKLOG.md).
Source: owner, 2026-10-09 — first Conflict parity gaps (G-1, row CP-07 in
[the parity tracker](../design/CONFLICT-PARITY.md)).

## Problem / outcome

In *Conflict: Desert Storm* an "advance to position" order also sets which way
the soldier faces when he gets there, so a squad can be posted watching a
doorway or a road. Sandline's move and hold orders carry only a point, so a bot
arriving with no threat in sight looks wherever its path ended.

## Scope

Conflict default (ADR-021), adapted to a mouse-and-wheel order with no extra
input: a move or hold order carries the **facing the issuing player was looking
in** when they gave it (desktop camera yaw, or the mobile orbit camera's yaw).
On arrival, with no threat to engage, the bot looks along that facing and keeps
it while holding. Threats, fire discipline (U-101) and attack orders still win.
The order marker shows the facing. Orders without a facing (old saves, bots'
own regroup) behave as today. The Order message gains an optional quantized
yaw, so `PROTOCOL_VERSION` bumps.

Out of scope: a separate control to rotate the facing while placing (a possible
follow-up if the owner wants finer control); formation facing for regroup.

## Acceptance criteria

- [ ] A move or hold order records the issuer's facing; the marker shows it.
- [ ] A bot that reaches its point with no visible threat faces that direction
      within a small tolerance and keeps facing it while holding.
- [ ] A visible threat, an attack order or fire discipline still take priority.
- [ ] Orders without a facing behave exactly as before.
- [ ] `PROTOCOL_VERSION` is bumped with its pinned tests; wire round-trip tested.
