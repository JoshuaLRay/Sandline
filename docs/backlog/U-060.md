# U-060 — Save the checkpoint's world in the campaign file

Epic: **Campaign**. Status, priority and dependencies live only in [BACKLOG.md](../../BACKLOG.md).
Source: split from [U-059](U-059.md) (its persistence criterion), owner direction 2026-09-30: a retry should be "just like the first time the campaign made it to that save point".

## Problem / outcome

U-059 restores the whole checkpoint world (enemies, spawner progress, soldier health, loadouts, ground pickups, placed devices, the clock) on a retry inside a running session. The campaign file (`persistCampaign`, `campaignSave`) still stores only the objective, elapsed time, spawn points, completed groups and the script's state, so after the host restarts or the room reloads, a resumed checkpoint has none of it: the world is rebuilt from `completedGroups` as before U-059.

## Scope

Add the U-059 snapshot to the saved checkpoint: a format version bump with a reader for the old version, size bounds (enemies are capped by `MAX_ENEMIES`, pickups and projectiles by their own caps), schema validation on load (a corrupt snapshot falls back to the old restore rather than failing the room), and the same downed-soldier rule (a snapshot is never saved with a soldier downed). Restore on room start (`startRoom`) as `retryMission` does.

## Acceptance criteria

- [x] A checkpoint saved by a running host is restored after a host restart with the same enemies, spawner progress, health, loadouts, ground pickups and placed devices.
- [x] An older save (no snapshot) still loads and behaves as it did.
- [x] A malformed or oversized snapshot is refused with a fallback and a log line, not a crash.
- [x] A round-trip test: save, rebuild the session from the file, and compare.

## Handoff / evidence

Implemented on `task/U-060-campaign-world`; awaiting review. No owner playtest verdict is claimed.

**What changed.** The saved checkpoint gains an optional `world` (enemies, spawner progress, soldiers' loadouts and health, ground pickups, placed devices, the mission clock), written by `persistCampaign` and read on load. The file's `formatVersion` stays 1: `world` is additive and carries its own `version` (`CHECKPOINT_WORLD_VERSION`), so an older save simply has none and loads as before. The database only bounds the size (`CHECKPOINT_WORLD_MAX_BYTES`, 512 KiB, past which the world is dropped and the basic checkpoint kept). The session validates on load (`parseCheckpointWorld`: known shapes, finite numbers, bounded lists); a world it refuses is logged (`console.warn`) and the room resumes from the basic checkpoint. A started session and a hosted room (`startRoom`) both restore the world as a retry does. Dead members a resumed spawner remembers as sent get negative ids, since a new process hands out the old enemy ids again.

**Evidence.** `packages/server/src/session/checkpointWorld.test.ts` (JSON round trip into a new session with the same enemies, health and places and nothing re-sent; an older save without a world; a malformed world refused with a warning; the parser's refusals; the database's size bound) and `encounterPressure.test.ts` (a hosted room restored from a saved checkpoint). `pnpm verify` and the CI jobs: see the PR.
