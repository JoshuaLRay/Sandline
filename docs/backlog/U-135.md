# U-135 — Version checkpoint data and preserve original mission-start state

Epic: Map implementation. Status, dependencies and work live in [BACKLOG.md](../../BACKLOG.md).
Source: implementation leaf of [U-113](U-113.md), Mission 1 specification §14.

## Scope

Add an optional positive integer `mapRevision` to world/level content, defaulting
to revision 1 for existing data. Persist the revision of newly captured
checkpoints without relabelling restored legacy or other-revision coordinates.
Keep the original six mission-start loadouts and start prisoner state separately
from the checkpoint's current squad inventory/pools. Validate and preserve these
fields through JSON/SQLite and repeated same-revision Session reload/restart.
Capture lobby starts at ready-up after loadout setup, and retain legacy save and
unrelated mission/run checkpoint behaviour.

This leaf supplies data/provenance; it does not claim incompatible-restore
quarantine or the required restart/select UI. Those are [U-136](U-136.md).
Cache stock remains U-133 in unmerged [#307](https://github.com/JoshuaLRay/Sandline/pull/307).

## Acceptance and verification

- World/level revision validation rejects malformed values; old data defaults
  to 1. The future replacement map must explicitly author revision 2.
- New checkpoints persist revision and validated mission-start snapshots.
  Current checkpoint inventory, 3D positions, armed timers and one-shot flags
  remain intact; reload/full restart returns original carry-over inventory.
- SQLite/JSON round-trips retain baseline prisoners and unrelated campaign
  progress/pools. Unknown legacy revision stays unknown on resave; another
  mission/run's checkpoint stays unchanged. Old saves remain parseable.
- Focused regressions, `pnpm verify`, applicable budgets/generators and all four
  latest-head CI jobs pass; implementation evidence is recorded.
