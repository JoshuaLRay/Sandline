# U-074 — Objectives in any order: parallel objectives and optional enemies

Epic: **Campaign design**. Status, priority and dependencies live only in [BACKLOG.md](../../BACKLOG.md).
Source: owner decisions on the campaign design, 2026-10-01 ([design doc](../design/CAMPAIGN.md)).

## Problem / outcome

A mission's objectives are a strict sequence today (`MissionRun` has one current objective, and each completion is a checkpoint). The owner wants objectives that can be done in whatever order the players choose, where applicable, without clearing every enemy.

## Scope

Let a mission data file group objectives into **stages**: the objectives in a stage are all open at once and may be completed in any order; the stage is complete when every *required* one is (an objective may be marked `optional`). Each completion is still a checkpoint, and progress, the HUD line, compass markers and the briefing show every open objective. Triggers and scripts keyed to `objective-start` and `objective-complete` keep working per objective. A mission with only single-objective stages behaves exactly as mission-01 does now. Proposal: no new objective types; `rescue`, `reach`, `destroy`, `upload` and `survive` are enough. **Not in scope:** removing `clear-and-hold` (it stays valid for the old mission), the escort (U-075), or any new mission's content.

## Start here

`shared/src/sim/mission.ts` (`MissionDef`, `OBJECTIVE_TYPES`, the `Mission` wire view), the server `MissionRun`, `shared/src/sim/events.ts` (objective triggers), `client/src/ui/missionHud.ts`, the checkpoint code in `Session.ts` (`captureMissionCheckpoint`). The `Mission` message is on the wire: a protocol bump and its tests are expected.

## Acceptance criteria

- [x] A mission file can declare a stage of several objectives; players can finish them in either order and the stage completes when the required ones are done.
- [x] An optional objective's completion is credited but not required; a checkpoint is saved at each completion and a retry restores which were done.
- [x] The HUD and briefing show every open objective (the compass has no objective markers today, so there is nothing to add there).
- [x] A mission with only sequential single-objective stages is unchanged (mission-01's tests and `sim-run --scenario mission --seeds 3`).
- [x] Headless coverage of both orders and of a retry mid-stage; `checkMission` validates stages.

## Handoff / evidence

Implemented on `task/U-074-parallel-objectives`; awaiting review. mission-01 is unchanged: `sim-run --scenario mission --all-missions --seeds 3` gives the same output as before this change.

**Data.** An objective may carry `stage` (0–15) and `optional`. The objectives of a stage are open together; the stage is done when every non-optional one is, and an optional one still open is dropped with it. All objectives of a mission name a stage, or none do (then each is its own stage, as before). Validated at parse: stages start at 0 and grow by at most one; each stage needs a required objective; at most one `upload` and one `rescue` per stage (the session's terminal, lever and rescue hold are single). `objectiveStages(mission)` gives the groups.

**Server.** `MissionRun` keeps a state per objective (progress, goal, phase, satisfied, done, breach) and steps every open one each tick; the view it publishes describes the first objective still to do (a required one before an optional) and lists the whole stage in `open` when it has more than one. Each completion is a checkpoint: the stage's first objective and which of its objectives are done (`checkpoint`, `checkpointDoneList`, `point`); `retry` and `restoreCheckpoint` resume with those done. The campaign file's checkpoint gains an optional `done`, additive (an older save has none). `Session` finds the upload to start, the lever and the terminal from the stage's open upload, awards objective XP and fires the upload message and the rescue per objective finished, requests a checkpoint at each, and the scoreboard counts objectives done.

**Events.** The host reports the objectives open and still to do (`objectives()`); `objective-start` fires as each opens, `objective-complete` as each stops being to do, `upload-start` for the stage's upload. The event checkpoint keeps `previousActive` (a save with the older `previousObjective` is read as before).

**Wire and HUD.** `Mission` gains the `open` list (`PROTOCOL_VERSION` 61); the HUD line lists every objective of a stage, ticking the done ones and naming the optional; the upload prompt reads the stage's upload. Callouts, the mission-sim leader and the briefing follow the described (first-to-do) objective, so a staged mission works with them unchanged.

**Evidence.** `server/src/session/stages.test.ts` (13: stage data and its refusals; either order; done stays done; optional; checkpoints inside a stage and restoring; an upload beside another objective; the events; the wire), `stagesSession.test.ts` (5, on a real session: either order, a retry inside the stage, the campaign file with and without `done`), `client/src/ui/missionHud.test.ts` (3). `pnpm verify` and the CI jobs: see the PR.

**Not here.** Any staged mission's content (mission 1 is U-065); bots choosing between a stage's objectives (the mission-sim leader follows the first to do); removing `clear-and-hold` (it stays valid).
