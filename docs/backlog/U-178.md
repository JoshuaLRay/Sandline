# U-178 — Return to Mission 1 for captured squad members after mission completion

Epic: Campaign. Pillar: P5 (every soldier matters), P6 (campaign rescue).
Size: L; intake needs decomposition before implementation.
Human verdict: integrated Mission 1 quality batched in U-119.
Status, priority, dependencies and branch/PR live in BACKLOG.md.
Source: owner steering, 2026-10-15; [CAMPAIGN D3 addendum](../design/CAMPAIGN.md#d3-owner-addendum--2026-10-15).

## Problem / outcome

The owner requires a forced Mission 1 rescue return after successfully completing
**any mission** with an imprisoned character in the active run's pool. Retrieve
captured squad members alongside Mission 1's original POW. Completing Mission 1
with prisoners still held requires another Mission 1 return. The replacement cell
must support six captives total: the original POW plus up to five squad members.

This is a new requested lifecycle, not an observed runtime regression. Exact
runtime reproduction and current behaviour have not been audited for this intake.
The stated new trigger is successful completion; failure and abandonment do not
gain a new trigger. Existing campaign/replay prisoner pool isolation and campaign
progress must remain intact.

## Scope

Decompose routing, durable pending-return/resume state, authored holding placement
and rescue integration into executable leaves before claiming runtime work.
Coordinate the placement contract with [U-144](U-144.md), rather than duplicating
it. Record how the correct next-run destination survives the forced return and
repeated Mission 1 runs without resetting campaign progress or duplicating
completed-mission entries and unlocks. Enforce the return on the authoritative
host path so ordinary or stale mission-select inputs cannot bypass it.

[U-175](U-175.md) constructs isolated physical capacity only. Its original POW
holding `(16,8,402)` and carried candidates `(12,8,400)`, `(20,8,400)`,
`(12,8,404)`, `(20,8,404)`, `(12,8,408)` are not yet a shared production contract.
Shared schema validation, deterministic slot mapping and rescue integration
remain needed. The current active old map cannot use these new coordinates;
replacement construction activation remains U-117. No runtime code is implemented
by this intake or by U-175.

## Acceptance criteria

- [ ] Split the runtime and placement work into focused leaves with dependencies,
  bounded scope and observable acceptance before promoting implementation READY.
- [ ] Successful completion of any mission with a nonempty active pool forces
  Mission 1, including repeated Mission 1 completion; empty pools retain normal
  selection. No newly invented failure/abandonment trigger.
- [ ] Original POW plus five captured squad members have six distinct supported,
  clear and rescue-accessible authored holdings with deterministic slot mapping;
  all six can be retrieved without replacing or losing another captive.
- [ ] Campaign and replay returns use only their respective pools; captures,
  rescues, inventory and checkpoints never overwrite the other run's state.
- [ ] Pending forced destination, captives and correct resume state survive
  retry, save/load, reconnect and repeated returns without freeing prisoners,
  bypassing rescue or duplicating state/progress.
- [ ] The host cannot bypass a pending forced return through mission select,
  ready-up or stale client requests; joining clients observe the same destination.
- [ ] After successful rescue, resume the correct campaign/replay destination
  with preserved campaign progress and completed-mission history; revisiting
  Mission 1 neither resets progress nor duplicates completion/unlock effects.
- [ ] Focused authoritative lifecycle/persistence/net/UI regressions and complete
  delivery gates pass on implementation leaves; human quality remains U-119.

## Verification

Test both run kinds with an empty pool, one captive and the five-carried-plus-
original six-captive maximum. Cover completion of a later mission and repeated
Mission 1, failed rescue/retry, save/load/reconnect, host choice rejection, pool
isolation and correct post-rescue resume/progress. Use actual authored placement
and rescue interactions; isolated geometry evidence cannot prove runtime routing.
Run pnpm verify and the required latest-head CI on the implementation leaves.
