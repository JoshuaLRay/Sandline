# U-089 — Run kinds in the campaign file, and separate prisoner pools

Epic: **Campaign design**. Status, priority and dependencies live only in [BACKLOG.md](../../BACKLOG.md).
Source: split from [U-072](U-072.md) (leaf 2 of 3), owner decisions 2026-10-01 (design doc D3).

## Problem / outcome

A character captured in a campaign run may be rescued only in the next campaign-run mission, never in a replay; one captured in a replay may be rescued only in the next replay run. The save has one prisoner pool (the soldier records' `captured` and `prisoner`), and a session does not know which kind of run it is.

## Scope

Extend the campaign file additively (the U-060 approach; older saves load as today): the kind of the run in progress (`campaign` or `replay`) and the world it is on, and a **prisoner pool per kind** (the existing fields read as the campaign pool). A session built from a save loads the pool of its run kind, writes captures into it, and leaves the other alone; completing a mission in a *campaign* run adds it to `completedMissions`, completing one in a *replay* run does not. Not in scope: choosing the next run (U-090).

## Start here

`server/src/persistence/CampaignDatabase.ts` (`CampaignState`, `SoldierSave`, `normalizedState`), `Session.ts` (`capturedAtStart`, `applyCaptured`, the completion handling near `campaignCompletedMissions`), U-061's tests (`captured.test.ts`), U-088's helpers.

## Acceptance criteria

- [x] The save carries the run kind and a pool per kind; an older save with neither loads as a campaign run with its existing prisoners.
- [x] A capture in a campaign run is held in the campaign pool and is rescued only in a campaign run; likewise for replay (session tests).
- [x] A replay completion does not add to `completedMissions`.
- [x] A host restarted mid-campaign resumes at the right mission and run kind (a campaign-file test).
- [x] `pnpm verify` green.

## Handoff / evidence

`CampaignState` gains, additively, `run?: 'campaign' | 'replay'` (absent: a campaign run; only a replay is written) and `replayPrisoners?: { slot, at }[]` (absent: none). The soldier records' `captured`/`prisoner` (U-061) ARE the campaign pool, so an older save keeps its prisoners where they were and loads as a campaign run. `normalizedState` validates both (bad run kind, more than six, repeated or non-finite entries are refused).

`Session`: `runKind` from the save; a campaign run starts with the campaign pool in play and writes this run's prisoners to the soldier records, carrying the replay pool through as loaded; a replay run starts with the replay pool, writes this run's prisoners to `replayPrisoners`, and writes the soldier records (the campaign pool) unchanged; `completedMissions` grows only in a campaign run. The save names the world and the kind, so a restarted host resumes there. Choosing the kind is U-090.

`pnpm exec vitest run packages/server/src/session/runKinds.test.ts`: 9 tests (both pools, a capture and a rescue in each kind, older save, no campaign progress in a replay, the database round trip, refusals). `pnpm verify`: green.
