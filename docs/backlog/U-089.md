# U-089 — Run kinds in the campaign file, and separate prisoner pools

Epic: **Campaign design**. Status, priority and dependencies live only in [BACKLOG.md](../../BACKLOG.md).
Source: split from [U-072](U-072.md) (leaf 2 of 3), owner decisions 2026-10-01 (design doc D3).

## Problem / outcome

A character captured in a campaign run may be rescued only in the next campaign-run mission, never in a replay; one captured in a replay may be rescued only in the next replay run. The save has one prisoner pool (the soldier records' `captured` and `prisoner`), and a session does not know which kind of run it is.

## Scope

Extend the campaign file additively (the U-060 approach; older saves load as today): the kind of the run in progress (`campaign` or `replay`) and the world it is on, and a **prisoner pool per kind** (the existing fields read as the campaign pool). A session built from a save loads the pool of its run kind, writes captures into it, and leaves the other alone; completing a mission in a *campaign* run adds it to `completedMissions`, completing one in a *replay* run does not. Not in scope: choosing the next run (U-090).

## Start here

`server/src/persistence/CampaignDatabase.ts` (`CampaignState`, `SoldierSave`, `normalizedState`), `Session.ts` (`capturedAtStart`, `applyCaptured`, the completion handling near `campaignCompletedMissions`), U-061's tests (`captured.test.ts`), U-088's helpers.

## Acceptance criteria

- [ ] The save carries the run kind and a pool per kind; an older save with neither loads as a campaign run with its existing prisoners.
- [ ] A capture in a campaign run is held in the campaign pool and is rescued only in a campaign run; likewise for replay (session tests).
- [ ] A replay completion does not add to `completedMissions`.
- [ ] A host restarted mid-campaign resumes at the right mission and run kind (a campaign-file test).
- [ ] `pnpm verify` green.
