# U-082 — Rectangular floors: bake, collide and draw only where the map is

Epic: **Campaign design**. Status, priority and dependencies live only in [BACKLOG.md](../../BACKLOG.md).
Source: [U-076](U-076.md), the large-map spike, 2026-10-01.

## Problem / outcome

A world's floor is a square of `floor.halfExtent` centred on the origin. A long three-lane map (120 x 480 m) needs a 1,000 x 1,000 m floor, which the navmesh bake treats as 100 million voxels: it takes 10 s at 250 m long and **fails** at 480 m ("Failed to create Detour navmesh data"). Cut to the lanes the same map is 6 million voxels and bakes in 2.5 s.

## Scope

Let a world file name a rectangular floor (proposal: `floor: { halfWidth, halfDepth }`, with `halfExtent` still meaning a square, so every committed world is unchanged, and an optional centre). The navmesh bake (`worldSoup`, and so `navBakeHash`), the collision floor and edge (`World.floorHalfExtent` is read by the character controller and the renderer; keep a derived `floorHalfExtent` for old callers), and the ground the client draws all use it. The bake also builds its bare mesh once for the vault links and once for the final mesh; reuse it where possible. `pnpm gen:nav` must rebake every committed world byte for byte (their floors are squares).

## Start here

`shared/src/sim/world.ts` (`loadWorld`, `floorHalfExtent`), `shared/src/sim/level.ts` (`floor`), `tools/src/nav/bake.ts` (`worldSoup`, `boxSoup`, `bakeWorld`, `meshLinks`), the renderer's ground (`client/src`), `tools/src/spike-large-map.ts` (square versus tight). A level format change: the committed bakes' hash covers `floorHalfExtent`.

## Acceptance criteria

- [x] A level can name a rectangular floor (`floor: { halfWidth, halfDepth }`, x and z); a file that names a square (`halfExtent`) gives the same world as before, and a file naming both, or half a rectangle, is refused.
- [x] The bake uses the real floor: a rectangular world bakes over the rectangle only (a lane 20 x 100 m: the length is walkable, the ground beside it and beyond its ends is not).
- [x] `pnpm gen:nav` rebakes every committed world byte-identically (their floors are squares; the bake hash only gains the rectangle's sides when they differ).
- [x] Tests: `world.test.ts` (the rectangle, the square unchanged, the refusals, through a level file), `bake.test.ts` (the soup, the mesh's extent, the hash).

## Handoff / evidence

Implemented on `task/U-082-rect-floor`; awaiting review.

**What changed.** `World` gains `floorHalfWidth` (x) and `floorHalfDepth` (z); `floorHalfExtent` is kept and is the larger of the two (the side of the smallest square that holds the floor), so callers that read it are unchanged. `loadWorld` takes `floor: { halfExtent }` (a square, as before) or `floor: { halfWidth, halfDepth }`. `boxSoup` takes a number or `{ halfWidth, halfDepth }` and `worldSoup` passes the real sides; `navBakeHash` adds the two sides only for a rectangle, so every square world keeps its hash. `level-check`'s renders draw the rectangle.

**A correction to the card.** It listed the collision floor and the renderer's ground as users of the floor. Neither is: the ground is not a collider (the controller clamps nothing to it) and the client draws its ground from the level's pieces, so the floor is read only by the navmesh bake and the `level-check` review renders. The change is therefore small.

**Effect.** The spike's 120 x 480 m map, which failed to bake on the square floor it needed (1,000 x 1,000 m, 100 million voxels), bakes over its own 6 million voxels in about 2.5 s (U-076's measurements). The spike tool itself still bakes a square floor in its default mode; it can name a rectangular floor now.
