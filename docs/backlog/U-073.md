# U-073 — Register a mission in one place; checks and the mission sim cover every mission

Epic: **Campaign design**. Status, priority and dependencies live only in [BACKLOG.md](../../BACKLOG.md).
Source: [U-071](U-071.md), 2026-10-01.

## Problem / outcome

Adding a mission means editing about eight places by hand, and the mission sim and the level checker are fixed to
`mission-01`. With four more missions planned, each would repeat the work and each place is a chance to forget one.

## Scope

INBOX: independent of the mission content, ready to scope on the owner's go. One registry: a mission's world, level,
encounter, script, mission file and (generated) navmesh found by id from its files, so a new mission is its data files plus
one line (or none). The checks follow: `level-check`'s join table moves into the level file or a sidecar; `sim-run
--scenario mission` takes `--mission <id>` and `--all-missions` already discovers files, so the default run covers every
registered mission; the lobby list is built from the registry (or from U-072's campaign data). A short "add a mission"
checklist goes in `docs/COMMANDS.md`. No behaviour change for mission-01.

## Start here

`shared/src/sim/world.ts` (the world registry), `sim/mission.ts`, `sim/encounters.ts`, `sim/scripts.ts` (script lookup), `server/src/ai/nav/baked`,
`client/src/ui/Lobby.ts`, `tools/src/level-check.ts`, `tools/src/scenarios/mission.ts`. `packages/shared/CLAUDE.md` for the shared package's rules.

## Acceptance criteria

- [x] A second mission can be added by adding data files and at most one registry line; a test adds a throwaway fixture mission to prove it.
- [x] `level-check`, `check:assets`, `check:packs` and the mission sim run over every registered mission.
- [x] mission-01 behaves exactly as before (its tests and `sim-run --scenario mission --seeds 3` are unchanged).
- [x] `docs/COMMANDS.md` has the "add a mission" checklist.

## Handoff / evidence

Implemented on `task/U-073-mission-registry`; awaiting review. Nothing about mission-01's behaviour changed.

**What changed.** `shared/src/sim/campaignRegistry.ts` lists each world with its mission, encounter, script and lobby label as one entry (`COMMITTED`); `world.ts`, `mission.ts`, `encounters.ts` and `scripts.ts` build their tables from it with `worldsFrom`, `missionsFrom`, `encountersFrom` and `scriptsFrom`, each of which takes any list of entries and refuses one whose file names another id, naming the entry. The lobby's `LOBBY_MAPS` is `lobbyMaps()`. `docs/COMMANDS.md` has the "Adding a mission" checklist.

**A correction to the card.** Several of the "places" the card listed were already generic: `gen:nav` bakes every registered world, `level-check` and `check:assets` find levels from their files, and `sim-run --scenario mission --all-missions` plays every file in `data/missions/`. `level-check`'s join table holds only the two legacy levels' exceptions; a new level has none, so it is not a place to edit. The hand-edited places were the four shared tables and the lobby; those are now one entry. The default `sim-run --scenario mission` (no flag) still plays mission-01 only, since its thresholds are tuned to it (`--all-missions` is the run that covers every mission, and CI runs both).

**Evidence.** `campaignRegistry.test.ts` (5): the committed tables match the registry; the lobby order; a throwaway `fixture-01` (mission-01's files copied under another id) found by all four builders and the lobby with no other edit; a mismatched world or mission id refused; a script with no mission refused. `pnpm gen:nav` rebakes every world byte-identically. `pnpm verify` and the CI jobs: see the PR.
