## Before you start

### Check the host (one minute, before inviting anyone)

- `curl https://sandline-host.fly.dev/healthz` — the host sleeps when
  nobody is connected, so the first request can take a few seconds. Record
  `protocol` (this build's is **33**; a page and a host that disagree
  refuse with `bad version`), `keyRequired` (if `true`, you need the join
  key in the lobby's **Key** field), `rooms` / `maxRooms` (4 on the
  deployed host, `fly.toml`) and `draining` (should be `false`).
- **The identity secret decides whether section 7 can pass.** A campaign
  is restored by its code, but the campaign's owner and your XP credit
  hang off your anonymous player ID, which the host signs with
  `IDENTITY_SECRET`. Unset, the host makes a random one at every boot, so
  your ID is refused as `bad identity` after the machine restarts — and on
  Fly the machine **stops itself whenever nobody is connected**, so it
  will have restarted by tomorrow (`docs/DEPLOYING.md`, "The identity
  secret"). Check before day one, from the host's boot log (the line with
  `identitySecret`: `N configured` or `random - identities do not survive
  a restart`) or with `fly secrets list`. Identity: ______
- The **Host** workflow deploys on demand: confirm the host is running the
  build you think it is (the protocol number above is the quick check).

### Controls

Checked against `client/src/input/LocalInput.ts`, `client/src/main.ts` and
the menu's key list (`client/src/ui/menu/settings.ts`):

- `W A S D` move, `Shift` sprint, `Space` jump / vault, `C` crouch
  (toggle; holding `Ctrl` also crouches, but only once a click into the
  game has gone fullscreen with the keyboard lock), `Z` prone.
- `LMB` fire, `RMB` aim (into first person), `R` reload, `V` swaps
  shoulder in third person or leaves first person.
- Number keys are **fixed per weapon, not per loadout**: `1` MK4 Carbine,
  `2` LR-9 Marksman, `3` M12 Breacher, `4` P7 Sidearm; in a host room only
  your class's guns answer (Team Leader: `1` and `4`; Marksman: `2` and
  `4`). `5` frag, `6` rocket; hold `G` to aim a quick throw, release to
  throw.
- `E`: **press** to man or leave the mounted gun; **hold** to revive a
  downed squadmate (the revive has first claim on the same press).
- `Q` hold for the order wheel (the mouse picks, `1`–`6` a slot, `7`–`8`
  a fireteam, `0` everyone; release to order); `F` marks what is under
  the crosshair.
- `Tab` (hold) scoreboard. `Esc` pause menu (Resume, Settings, Leave; the
  session runs on). `P` plays again once the mission is won or lost — after
  a failure it retries from the last checkpoint if there is one.
- `H` shows the QA readouts (they start folded; the fps is in them). `N`
  folds the netgraph. `B` the AI debug overlay (the deployed host allows it:
  `AI_DEBUG = "1"` in `fly.toml`).

### What the build does and does not contain (found in prep)

These are facts about the code at the time of writing, so the session is
not spent looking for something that is not there.

- **No committed mission has several objectives, a scripted event or a
  reachable checkpoint.** `data/missions/` holds `mission-01.json` and
  `greybox-01.json`, one objective each (clear and hold). T-4.15's
  authored event scripts (messages, doors and gates, flags) have a parser
  but no data file, and the host builds every room with an empty script.
  A checkpoint is recorded when an objective completes, so with one
  objective there is never one to retry from: `P` after a failure is a
  full restart. What a host room *does* run through T-4.15's event runner
  is the encounter's own triggers: the start groups, the assault-entry
  group, the counterattack on the garrison's death and the 300 s group.
  Section 4 is written for whichever of these is true when you play.
- **The campaign code is the room code.** On the deployed host, **Host a
  room** makes a campaign: its code is eight characters (region-tagged in
  the invite link, like `A-KM7XRT34`) and it is the code the room lobby
  shows. It is saved when an objective completes and when a mission ends,
  won or lost. The next day it is typed into **Room code** and joined.
- **XP belongs to the slot's soldier.** The campaign saves six soldiers,
  one per slot, and a human earns onto the soldier of the slot they are
  in. Saved XP shows only on the mission-end line, one per soldier you
  played: "Soldier N: you earned N XP · rank · N XP total". There is no
  screen that shows saved totals on joining, so the day-two check is the
  "total" after another mission — in the **same slot** as day one.
- **The class is picked again each session.** The save records each
  slot's class, but a room assigns classes from this session's picks and
  the slot defaults (`Session.ts` starts them empty), so a restored
  campaign does not put your class back by itself, as far as the code
  reads.

  of the grey-box mission complete 0 of 6, all squad wipes. A loss to the

  scripting, unless the mission did something wrong (did not start, did
  not count, did not end).

  Judge whether the level reads as a place under that light, not whether
