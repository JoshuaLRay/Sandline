# T-4.12 — baked-lighting spike

**Date:** 2026-09-24  
**Outcome:** take PLAN.md's explicit fallback: hemisphere light + the one shadow-mapped sun + baked ambient occlusion per static piece.

## What the spike found

The blocker is not choosing a light-transport solver. It is the geometry contract that a level lightmap would have to land on.

The T-4.04/T-4.10 kit deliberately tiles **UV0** into shared family-atlas cells. Repeated walls, ground tiles and props therefore reuse the same texture coordinates. T-4.07 then batches every repeated asset as an `InstancedMesh`, sharing that geometry and material across placements. The generated static source meshes do not carry `TEXCOORD_1`.

A conventional level lightmap needs the opposite ownership: each placed surface needs unique UV2 atlas space (or a per-instance lightmap transform plus a shader/material path that understands it). Creating unique geometry per placement would throw away the instancing path whose draw-call probe is already the ADR-013 guard. A Chromium progressive lightmapper and a small CPU path tracer both hit the same output problem; changing the transport solver does not create unique UV2 ownership.

Run:

```
pnpm bake:light
```

The command inspects `mission-01` (or a supplied level id), its repeated placements and the source glTF primitives, and prints the evidence and outcome. It writes no files.

## Fallback implemented

`packages/client/src/assets/lightmaps.ts` performs a deterministic **one-time vertex AO bake** when a static piece template is loaded:

- a fixed hemisphere of short rays is traced against the piece's own static triangles;
- the resulting scalar is written to the geometry's vertex-colour attribute;
- the material enables vertex colours;
- T-4.07's instances then all share that baked geometry.

This is not realtime GI and not screen-space AO. It adds no lightmap texture, network data, runtime draw call or per-frame tracing. The existing hemisphere light remains the sky fill, and the existing hard shadow-mapped sun remains the dynamic shadow source.

The tradeoff is deliberate: per-piece AO captures creases, overhangs and self-occlusion inside a kit piece, but not shadows caused by one separately placed piece onto another. That is the quality ceiling of the fallback named in the task.

## Verification

- `packages/tools/src/bake-light.test.ts` pins the spike against the committed `mission-01` sources.
- `packages/client/src/assets/lightmaps.test.ts` verifies that a vertex beside an occluder bakes darker than one beyond the AO radius, and that baking shared template geometry is idempotent.
- The existing Chromium `drawBudget.browser.test.ts` remains the draw-call gate for `mission-01`; the fallback changes vertex data only and does not introduce a new render object or material pass.

If full level lightmaps are revisited, the prerequisite is a UV2/atlas ownership design compatible with instancing (for example per-instance lightmap atlas transforms in the material), not a different ray tracer.
